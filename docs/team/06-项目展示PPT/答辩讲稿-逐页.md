## P5 系统架构（1 分 30 秒）★结构层次①

【幻灯片画面】自上而下的分层架构图：

```
浏览器（前台 / 成员中心 / 管理后台 三套界面）
        ↓ 统一入口 index.php 路由分发
控制器层（13 个控制器，按模块划分）
        ↓
模型层（15 个模型，封装全部 SQL 与业务规则）
        ↓
MySQL 8.0（21 张表 + 3 个视图）
```
侧边标注：视图层三套布局（前台 Clean 风格 / 成员中心 / 后台 AdminLTE 风格）；静态资源 Bootstrap 5 + ECharts；部署 Docker Compose。

【讲稿】
接下来讲系统的结构层次，分四层从上往下看。

最上层是表现层：我们做了三套界面——访客看的前台、成员用的个人中心、管理员用的后台，三套布局共享同一套设计语言。

所有请求进入统一入口 index.php，由路由分发到控制器层。我们按业务模块拆了 13 个控制器，比如成员、项目、公告、留言、认证、资源、数据包、健康检查，每个控制器只做请求处理和流程编排，不写 SQL。

再往下是模型层，15 个模型把全部 SQL 和业务规则封装起来，控制器和模型严格分层，这是我们对 MVC 的落地。

最底层是 MySQL 8.0，21 张数据表加 3 个视图支撑全部业务。整个应用用 PHP 8.2 编写，前端基于 Bootstrap 5 加原生 JavaScript，图表用 ECharts，整体通过 Docker Compose 编排，一条命令即可部署。

> 【旁注——若被问"13 和 15 具体是哪些"】
> **13 个控制器**：Admin（后台聚合）· Announcement（公告）· Auth（认证）· Datapackage（数据包）· Health（数据健康）· Home（首页）· Me（成员中心）· Member（成员主页）· Message（留言）· Project（项目）· Resource（资源）· System（探活/错误页）· Team（团队介绍）
> **15 个模型**：Analytics · Announcement · Auth · Dashboard · DataPackage · Health · Log · Media · Member · Message · Project · Resource · SiteSetting · Team · User
> 记忆口径：控制器按"页面模块"拆，模型按"数据表族"拆——看板/统计类是跨表聚合所以单独成模型。

## P6 数据库设计（1 分 30 秒）★结构层次②

【幻灯片画面】左侧：21 张表按五组分类的表格图（账号权限 4 / 内容 10 / 资源 2 / 站点 1 / 运维 4）；右侧：核心 E-R 关系图（用户—角色—权限、成员—项目—技能、留言—回复）。

【讲稿】
数据库是这门课的核心，我们重点讲设计思路。

21 张表按职责分五组：账号权限组 4 张，采用 RBAC 模型，用户通过角色获得权限，权限精确到功能点；内容主体组 10 张，覆盖团队资料、成员、项目、公告、留言及其回复；资源组 2 张管理上传文件与下载资源；站点设置 1 张；运维组 4 张记录访问、登录日志和操作审计。

几个关键设计：一是所有内容表的外键、索引齐全，支持高效分页与筛选；二是消息表与用户表分离敏感信息，IP 只存加盐哈希；三是提供了 3 个视图简化统计查询；四是 install.sql 支持空库一次性安装，21 张表一次导入即可运行。

## P10 技术亮点②：数据包——整站一键迁移（1 分 30 秒）★自研特色

【幻灯片画面】流程图：后台一键导出 → 数据包 ZIP（data.sql 全表数据 + uploads 上传文件 + manifest 校验清单）→ 换服务器/回滚时一键导入；旁边配一张前后对比小图。

【讲稿】
接下来是我们最有特色的功能：数据包。

我们的架构有一个原则——代码仓库是纯模板，不含任何真实数据；真实内容全部在数据库和上传文件里。那么换服务器、或者想回到某个历史状态时怎么办？我们在后台实现了数据包机制：一键导出，系统会把全部 21 张表的数据、上传的图片文件、以及一个记录 schema 版本和行数的校验清单，打包成一个 ZIP；需要时一键导入，整站数据恢复到快照时点。

它解决了三个实际问题：第一，数据与代码彻底解耦，仓库里没有任何真实信息；第二，整站迁移从人工导库变成一键操作；第三，配合导入的版本校验——数据包如果由更新版本的代码导出会被拒绝——避免了结构不兼容导致的恢复失败。

## 附 B：答辩 Q&A 预案（预测问题 + 回答要点）

| 可能的问题 | 回答要点 |
| --- | --- |
| 为什么不用 Laravel/ThinkPHP 框架？ | 课程重点是理解 MVC 本质，自建轻量 MVC 让我们对路由、ORM、会话的实现完全可控；依赖少、部署简单（ADR-01 决策，代价是用约定与基类控制重复） |
| 21 张表怎么划分的？有没有冗余？ | 五组职责划分；举例 page_views 与 login_logs 分表是因为写入模式不同；核心内容表满足三范式，view_count 等少数冗余字段是为列表页性能有意为之 |
| 密码安全怎么保证？ | bcrypt 散列存储；初始账号首登强制改密；登录失败锁定与 IP 限流防爆破；session 属性 HttpOnly+SameSite |
| 数据包和 mysqldump 的区别？ | 数据包是产品化能力：面向非技术用户、带版本校验与二次确认、整库+文件一体；mysqldump 是运维兜底手段，两者并存 |
| PPT 里 `DatapackageController` 小写 p、`DataPackageModel` 大写 P，命名为何不一致？ | 入口路由按 `ucfirst(strtolower(?r=控制器名))` 解析（`code/public/index.php`），多词驼峰控制器名经路由归一化后不可达，控制器名只能取路由单词本身；模型不经路由、遵循标准 PascalCase。该差异由路由约定决定，PPT 所写与仓库实际文件一一对应，可当场核对 |
| 工作量怎么分配和衡量？ | 工作量以模块分工体现：后端、前端、文档、管理四大块边界清晰，每人负责的模块都能对应到仓库中的文件与文档；Git 提交记录可当场验证。我们刻意不使用简单数字百分比，因为文档、代码与运维工作的复杂度不同，数字反而失真 |
| 遇到的最大困难？ | 举例：空数据边界缺陷（有数据时正常、空库部署即崩溃）——通过空库全页面测试发现并修复；说明我们的质量方法是"测试到没测过的状态"，而不是只测跑得通的路径 |
